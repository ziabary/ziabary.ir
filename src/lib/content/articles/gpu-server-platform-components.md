سرور GPU مجموعه‌ای از کارت‌های گران‌قیمت در یک شاسی نیست. ارزش سامانه به ضعیف‌ترین حلقهٔ مسیر داده محدود می‌شود: storage کند، CPU نامتناسب، RAM ناکافی، توپولوژی PCIe نامطلوب یا هوای ناکافی می‌تواند GPU را بیکار یا throttled نگه دارد. طراحی درست از workload و مسیر داده آغاز می‌شود و سپس اجزای سرور را متوازن می‌کند.

## CPU: فقط تعداد هسته مهم نیست

CPU داده را آماده می‌کند، decode و tokenization را انجام می‌دهد، jobها را هماهنگ می‌کند و I/O را مدیریت می‌کند. نیاز آن میان inference یک مدل زبانی و آموزش بینایی ماشین با augmentation سنگین یکسان نیست.

در انتخاب CPU این موارد را با هم ببینید:

- تعداد laneهای PCIe و نسل آن‌ها؛
- تعداد کانال‌های حافظه و پهنای‌باند RAM؛
- تعداد socket و مرزهای NUMA؛
- توان تک‌رشته برای مراحل غیرموازی؛
- تعداد هسته برای preprocessing و چندمستاجری؛
- مسیر مستقیم GPU و NIC به root complex.

CPU با هستهٔ بیشتر اگر lane کافی برای GPUها نداشته باشد، انتخاب بهتری نیست. در پیکربندی دوپردازنده‌ای نیز scheduler و pinning باید locality حافظه، GPU و NIC را رعایت کنند.

## RAM: از footprint مسیر کار محاسبه کنید

نسخه‌هایی مانند «۸ گیگابایت کافی است» یا «RAM باید درصد ثابتی بیشتر از مجموع VRAM باشد» قانون عمومی نیستند. RAM ممکن است dataset cache، tokenizer، workerهای data loader، offload مدل، vector database محلی، filesystem cache و چند job همزمان را نگه دارد.

برای sizing، peak مصرف هر workload نماینده را اندازه بگیرید، هم‌زمانی را اعمال کنید و برای رشد و failure حاشیه بگذارید. اگر training از CPU offload استفاده می‌کند یا داده پیش از ورود به GPU expand می‌شود، RAM می‌تواند چند برابر حالت inference ساده باشد. ظرفیت بالا بدون bandwidth کافی هم مسئله را کامل حل نمی‌کند؛ تعداد DIMM و کانال فعال اهمیت دارد.

## PCIe و NUMA: نقشهٔ داخلی سرور

هر GPU باید با نسل و عرض لینک مورد انتظار بالا بیاید. شیار فیزیکی x16 ممکن است الکتریکی x8 باشد یا پهنای‌باندش را پشت PCIe switch با چند کارت شریک شود. در سرور دو socket، عبور ترافیک GPU از CPU دیگر latency و ازدحام اضافه می‌کند.

نمودار topology سازنده و خروجی ابزارهایی مانند `nvidia-smi topo -m` بخشی از سند پذیرش‌اند. [راهنمای پیکربندی NVIDIA-Certified Systems](https://docs.nvidia.com/certification-programs/latest/nvidia-certified-configuration-guide.html) نیز تأکید می‌کند که پیکربندی بهینهٔ PCIe به workload وابسته است و نسخهٔ واحدی برای همه وجود ندارد.

## ذخیره‌سازی: سه لایه با سه هدف

بهتر است storage را حداقل در سه نقش ببینید:

1. **سیستم‌عامل و ابزارها:** کوچک، قابل بازسازی و جدا از دادهٔ کاری؛
2. **scratch/cache/checkpoint محلی:** پرسرعت و متناسب با شدت نوشتن؛
3. **داده و artifact پایدار:** دارای سیاست حفاظت، نسخه‌بندی و backup متناسب با ارزش داده.

RAID همیشه پاسخ یکسانی ندارد. dataset قابل بازیابی ممکن است به حفاظت کمتری نیاز داشته باشد، اما checkpoint چندروزه یا دادهٔ یکتا نباید با خرابی یک دیسک از بین برود. ظرفیت نیز باید از اندازهٔ داده، نسخه‌های مدل، checkpointها و نرخ رشد به دست آید؛ نه عدد ثابت ۲۰ یا ۱۰۰ ترابایت.

برای آموزش در مقیاس، throughput و IOPS باید با تعداد GPU رشد کنند. [MLPerf Storage](https://mlcommons.org/benchmarks/storage/) دقیقاً توان storage برای تغذیهٔ شتاب‌دهنده‌ها و checkpointing را می‌سنجد. NVMe زیاد روی کاغذ مفید نیست اگر مسیر PCIe آن با GPUها oversubscribed باشد.

## شبکه: مدیریت، سرویس و fabric را جدا کنید

سه نوع ترافیک ماهیت متفاوت دارند:

- **مدیریت:** BMC، مانیتورینگ و کنترل با دسترسی جداشده؛
- **داده و سرویس:** ورود dataset، API و دسترسی کاربران؛
- **cluster fabric:** ارتباط collective، RDMA و storage پرسرعت میان nodeها.

سرعت شبکه از تعداد GPU به‌تنهایی تعیین نمی‌شود. jobهای مستقل ممکن است با شبکهٔ معمولی کار کنند؛ آموزش توزیع‌شده می‌تواند به ۲۰۰/۴۰۰/۸۰۰GbE یا InfiniBand و طراحی بدون oversubscription نیاز داشته باشد. NIC باید از نظر NUMA نزدیک GPUهای مصرف‌کننده باشد و MTU، RDMA، routing و switch buffer به‌صورت end-to-end آزموده شوند.

NVSwitch شبکهٔ بین سرورها نیست. NVSwitch fabric داخل سامانهٔ HGX را می‌سازد؛ ارتباط nodeها همچنان NIC و switch شبکهٔ مناسب می‌خواهد.

## برق و خنک‌کاری: ظرفیت پیوسته، نه عدد نامی

توان GPU فقط بخشی از بار است. CPU، DIMM، NVMe، NIC و فن‌ها نیز مصرف دارند و با افزایش دمای ورودی، فن‌ها توان بیشتری می‌گیرند. طراحی باید وضعیت از دست‌رفتن یک PSU را نیز پوشش دهد؛ N+1 واقعی یعنی سامانه پس از خرابی یک منبع هنوز بار مجاز را بدون خاموشی یا power cap ناخواسته تحمل کند.

در خنک‌کاری، active و passive بودن GPU تعیین‌کننده است. کارت passive به فشار و جهت هوای طراحی‌شدهٔ شاسی وابسته است؛ کارت open-air مصرفی گرما را داخل شاسی پخش می‌کند. دمای متوسط پایین کافی نیست: hotspot، حافظه و VRM باید در بار پیوسته کنترل شوند.

## مدیریت، firmware و مشاهده‌پذیری

پشتهٔ عملیاتی باید نسخه‌های BIOS، BMC، GPU firmware، driver، CUDA/ROCm، Fabric Manager و container runtime را به‌عنوان یک ماتریس سازگاری نگه دارد. ارتقای تک‌جزئی و بدون rollback می‌تواند سامانهٔ سالم را از کار بیندازد.

حداقل telemetry شامل utilization، memory، power، temperature، clock، throttling reason، ECC، XID، خطاهای PCIe و سلامت NIC/storage است. برای چندمستاجری نیز quota، accounting و جداسازی داده لازم‌اند. خرید سخت‌افزار بدون برنامهٔ scheduler، مانیتورینگ و ظرفیت‌سنجی معمولاً به utilization پایین منتهی می‌شود.

## معیار طراحی متوازن

برای هر workload نماینده این مسیر را ثبت کنید:

`storage/network → CPU/RAM → PCIe/NUMA → GPU memory/compute → خروجی`

سپس زمان انتظار هر مرحله، throughput، توان و خطا را اندازه بگیرید. ارتقای بخشی که GPU را منتظر نگه نمی‌دارد الزاماً هیچ کارایی اضافه نمی‌کند. هدف این نیست که همهٔ اجزا بیشینه باشند؛ هدف آن است که هیچ جزء پرهزینه‌ای به دلیل جزء ارزان‌تر بیکار نماند.

در نهایت، نام شاسی تضمین‌کننده نیست. [NVIDIA-Certified Systems](https://www.nvidia.com/en-us/data-center/products/certified-systems/) پیکربندی‌های مشخص را از نظر توان، حرارت، مکانیک و signal integrity اعتبارسنجی می‌کند. خرید نیز باید بر اساس همان BOM مشخص و آزمون workload واقعی انجام شود.
